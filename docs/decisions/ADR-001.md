# ADR-001: User and Organization Boundaries

- **Status:** PROPOSED
- **Date:** 2026-11-13 (baseline documentation)
- **Decision owner:** Not recorded

## Context

The `users` app has a `User` and an overloaded `Profile`. This checkout also contains an `organizations` app with `Organization` and `OrganizationMembership`. The Phase 0 audit identified mixed business concerns in Profile and tenant-boundary risk.

## Problem

Person identity, business ownership, and organization-scoped access must not be conflated. All tenant-owned data and operations need a consistent authorization boundary.

## Proposed direction

Treat `User` as a person/account and `Organization` as a business tenant. Use `OrganizationMembership` to associate a user with an organization and represent organization-scoped access. Move organization-specific fields out of Profile only through an explicit compatibility-preserving migration.

## Consequences and verification

This direction requires a role/permission matrix, audit of tenant ownership and every list/detail/search/export/file path, and a migration plan for existing Profile data. Model existence does not prove tenant isolation. No change is approved by this proposal alone.

## Alternatives considered

- Keep all business and provider data embedded in Profile: rejected as a long-term boundary because it perpetuates overloaded identity and weak tenancy.
- Introduce organization membership and preserve current profile behavior during migration: preferred proposed direction.
